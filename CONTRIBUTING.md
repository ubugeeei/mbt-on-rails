# Contributing to `mbt_on_rails`

Thanks for thinking about contributing. This project is a Rails-inspired framework written in MoonBit; contributions ship via pull requests and pass through the same CI gate every time.

## Toolchain

The pinned MoonBit toolchain lives in [`.github/actions/setup-moonbit/action.yml`](.github/actions/setup-moonbit/action.yml). At the time of writing CI verifies against:

- `moon` — `0.1.20260512 (81d40e3 2026-05-12)`
- `moonc` — `v0.9.2+bbe2b338f (2026-05-12)`
- `moonrun` — `moonrun 0.1.20260512 (81d40e3 2026-05-12)`

If you upgrade or downgrade locally make sure those values still match before opening a PR. Older toolchains have been known to segfault on this codebase.

## Local gate

Before pushing, run the same checks CI runs:

```bash
moon info
moon fmt
git diff --exit-code           # fail if `moon info` or `moon fmt` changed anything
scripts/check_moon_warnings.sh # zero-warning policy
moon build                     # default target
moon test                      # default target
```

Once that is green, repeat `moon build` and `moon test` against `--target js`, `--target wasm-gc`, and `--target native` to mirror the CI matrix.

## Tests

- Public-surface tests live under [`tests/public/`](tests/public/) and run against the published `mbt_on_rails` facade through [`tests/public/prelude.mbt`](tests/public/prelude.mbt). Whenever you add a new public function, type, or method, list it in the prelude and add at least one happy-path and one negative-path test there.
- Internal whitebox tests live next to the implementation as `*_wbtest.mbt` files. Use them for invariants that should not be part of the public contract.
- Tests must be runnable on every CI target (default, js, wasm-gc, native).

## Public API surface

The contract is whatever appears in:

- [`mbt_on_rails.mbt`](mbt_on_rails.mbt) — the public facade. Anything not re-exported here is an internal detail.
- [`pkg.generated.mbti`](pkg.generated.mbti) — regenerated by `moon info`. Treat changes to this file as API surface changes and call them out in the PR description.

Internal `*_wbtest.mbt` files and anything inside `src/<pkg>/` that is not re-exported through the facade may change without notice.

## Commits and PRs

The commit cadence so far follows `area(scope): imperative summary` (see `git log` for examples — e.g. `security(http): default-deny external schemes in redirect_response`). Stick to that shape; the area prefix helps future contributors scan history.

Each PR should:

1. State the user-facing change in two or three lines at the top of the description.
2. Link the issue it closes.
3. Include a short test plan (what new tests were added, what was verified locally).
4. Keep the diff focused. If you find yourself fixing several unrelated things, split them into separate PRs.

We avoid `Co-Authored-By: <bot>` trailers and ship-style emoji footers. Plain human commit messages.

## Security disclosure

For anything that looks like it could be exploited, please **do not open a public issue**. Use GitHub's "Report a vulnerability" form on the repository's Security tab. A maintainer will route it from there.
